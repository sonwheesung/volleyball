# 마이그레이션 주의사항 (Migration Cautions)

> 데이터 구조·규칙을 바꿀 때 **기존 사용자 데이터가 깨지지 않게** 옮기는 절차의 주의사항.
> 배구명가는 **두 종류의 마이그레이션**이 있고 성격이 완전히 다르다 — 헷갈리면 사고 난다.
>
> - **클라이언트 세이브 마이그레이션** — 기기 로컬 세이브(zustand persist). `store/saveMigration.ts` `SAVE_VERSION`+`migrateSave`.
> - **서버 DB 스키마 마이그레이션** — Supabase/Postgres. drizzle. 여러 사용자가 동시에 물려 있어 훨씬 위험.
>
> 정본 참조: 세이브 = `docs/SAVE_SYSTEM.md` · 서버 = `docs/BACKEND_SYSTEM.md` §13.7 + 메모리 `prod-schema-migration-caution`.

---

## 0. 착수 전 — 어느 쪽인가부터 (가장 자주 헷갈림)

| | 클라이언트 세이브 | 서버 DB 스키마 |
|---|---|---|
| 대상 | 기기 로컬 1개 세이브 | 전 사용자 공유 테이블 |
| 도구 | `SAVE_VERSION`+`migrateSave` | drizzle `generate`+`migrate` |
| 되돌리기 | 사용자별 독립(백업/복구 채널) | 전 사용자 영향 — 롤백 어려움 |
| 핵심 위험 | 리플레이 재계산·아카이브 훼손 | 파괴적 DDL(NOT NULL·rename·drop) |
| 출시 후 | 버전 게이트로 안전 | **Expand/Contract 3단계 필수** |

> **먼저 "이게 로컬 세이브냐 서버 DB냐"를 확정**하고 아래 해당 절만 따른다. 재화·결제·계정·로그는 서버, 시즌/선수/특성/기록은 로컬 세이브다(결정론 격리 — `CLAUDE.md` 8장).

## 1. 클라이언트 세이브 마이그레이션 주의사항

배구명가 세이브 = **base 스냅샷 + currentDay + results(시드 리플레이)** + 아카이브(HOF·시즌기록·통산). `migrateSave(persisted, version)`가 로드 시 옛 버전을 정규화한다.

### 1.1 버전 게이트로 **일회성** — 매 로드 재적용 금지
- `SAVE_VERSION`을 올리고 `if (version < N) { ...변환... }` 게이트 안에서만 변환. 이미 마이그레이션된 세이브(version ≥ N)는 건드리지 않는다.
- **왜**: 매 로드 재적용되면 (a) 성능 낭비 (b) 비멱등 변환이면 데이터가 계속 변형된다. 게이트가 "딱 한 번"을 보장.
- 실사례(2026-07-27 특성 v4→v5): `version < 5` 게이트로 구세이브 선수 특성만 1회 재부여. version=5 입력은 무변환(가드 (e)로 봉인).

### 1.2 **결정론 변환만** — 랜덤 금지
- 변환은 같은 입력 → 같은 출력이어야 한다. id 시드 함수(`rollTraits(id)` 등)를 쓰고 `Math.random()`·시계는 절대 금지.
- **왜**: 세이브는 리플레이 기반이라 비결정 변환은 재현·검증 불가 + 재로드마다 결과가 흔들린다.

### 1.3 **바꿀 필드만 교체, 나머지 스프레드 보존**
- `{ ...player, traits: rollTraits(id) }` 처럼 **딱 한 필드만** 바꾸고 나머지는 원형 유지. career·계약·나이·스탯을 실수로 건드리지 않게.
- 가드로 "traits 외 전 필드 바이트 불변"을 확인(오늘 가드 (d)).

### 1.4 ★ **과거 아카이브는 절대 훼손 금지** (가장 위험한 함정)
- 명예의전당·시즌 연표·통산 기록(career totals)·우승 이력은 **append-only 히스토리**다. base 선수 데이터를 바꾸면 리플레이 재계산으로 **과거 결과가 소급 변경**될 수 있는데, **아카이브는 그 재계산 대상이 아니어야** 한다.
- **원칙**: 마이그레이션은 `playerBase`(현재/미래 시뮬 입력)만 만지고, **아카이브 top-level 필드는 코드가 아예 접근하지 않는다**(별개 영속 필드라 무접촉이면 보존).
- **검증(하드 요건)**: 마이그레이션 전 `{hallOfFame, archive, careerTotals, retirements}` JSON 지문을 떠서 **후와 바이트 단위 비교**해 동일함을 실측(오늘 가드 (c)). 설계상 안 건드린다 + 실측으로 확인 = 두 겹.

### 1.5 리플레이 재계산 파급 인지 (base 변경의 숨은 비용)
- base 선수 데이터(특성 등)를 바꾸면 `recordBump(0)`로 **전 시즌 결과 캐시가 무효화**되고, `ENGINE_VERSION` 게이트도 재계산을 강제한다 → **현재 진행 중 시즌의 이미 치른 경기가 새 데이터로 재계산**된다(결과가 소폭 달라질 수 있음).
- **미착수 시즌(0/N)이면 재계산할 현재 결과가 없어 깔끔**(특성만 갱신). 시즌 진행 중 세이브면 현재 시즌만 재계산(과거는 아카이브라 보존).
- 착수 전 "이 변경이 리플레이에 소급되나? 아카이브는 격리돼 있나?"를 반드시 자문.

### 1.6 손상 세이브 안전 복원
- 변환 중 손상 엔트리는 **제거하거나 기본값으로 coerce**하고 크래시시키지 않는다(부분 손상 세이브도 로드되게). `partialize` 키 == 복원 키 집합 유지(가드 `_dv_savescope`).
- 최후 복구는 서버 recoveryData 채널(메모리 `save-recovery-channel`).

### 1.7 세이브 마이그레이션 검증 배터리
- 신규 변환마다 전용 가드 + 기존 세이브 가드 회귀:
  - 전용: 변환 결과 정합(새 규칙 충족) + **결정론(2회 동일)** + **아카이브 바이트 불변** + traits외 필드 불변 + version 게이트 일회성 + **A/B 자가검증**(변환 스킵 뮤턴트면 정합 FAIL — 변환이 실제로 일어났는지 봉인).
  - 회귀: `_dv_migrate`·`_dv_migrate_e2e`·`_dv_save_transfer`·`_dv_save_corpus`(옛 버전 코퍼스 로드)·`_dv_save_backup`·`_dv_savescope`·`_dv_savesize` + `_dv_golden`(fresh 리그라 무영향 PASS 유지).

## 2. 서버 DB 스키마 마이그레이션 주의사항

여러 사용자가 동시에 물린 공유 테이블 — 훨씬 위험. 정본 메모리 `prod-schema-migration-caution` + `docs/BACKEND_SYSTEM.md` §13.7.

### 2.1 출시 전 vs 출시 후
- **출시 전(사용자 데이터 없음)**: 자유롭게 `drizzle push`. 파괴적 변경 OK.
- **출시 후(운영 데이터 있음)**: 파괴적 DDL(**NOT NULL 추가·컬럼 rename·drop**)은 배포 순간 기존 행/구버전 앱을 깬다 → **Expand/Contract 3단계 필수**.

### 2.2 Expand/Contract 3단계 (출시 후 파괴적 변경)
1. **Expand**: 새 컬럼을 **nullable/기본값**으로 추가(옛 코드·새 코드 둘 다 동작). 배포.
2. **Migrate/Backfill**: 데이터 채우고 새 코드가 새 컬럼을 쓰게 전환. 배포.
3. **Contract**: 모든 클라이언트가 새 버전으로 넘어간 뒤에야 옛 컬럼 drop/NOT NULL 강화.
- rename = "새 컬럼 추가 → 복사 → 옛 컬럼 제거"로 3단계 분해(직접 rename 금지).

### 2.3 배포 절차 (사고 예방)
- **마이그레이션 먼저(:5432 직결) → Vercel 배포 → 스모크**(deploy-prod 스킬/`docs/SERVER_OPS.md` §3). 마이그레이션은 `generate`+`migrate`(push 아님, 운영은 이력 관리).
- **vercel env 덮어쓰기 사고 주의**(메모리 `vercel-link-clobbers-env`): `vercel link/env pull`이 `.env.local`을 무경고 덮어씀 → 실행 전 `cp` 백업.
- 연결 규칙: 풀러(6543 `prepare:false`) vs 마이그레이션(5432 직결) — 호스팅 prod 전용(`BACKEND_SYSTEM` §13.7).

### 2.4 되돌릴 수 없음을 전제 — 백업·롤백 계획
- 운영 DDL은 롤백이 어렵다. 배포 전 백업 + "실패 시 어떻게 되돌리나"를 먼저 적는다.

## 3. 공통 원칙 & 착수 전 체크리스트

- **문서 먼저**: 마이그레이션 결정을 `SAVE_SYSTEM`/`BACKEND_SYSTEM`에 먼저 반영(취소선 정정으로 옛 결정 보존, `DOC_DISCIPLINE`).
- **추정 금지**: "이 변환이 X를 안 건드릴 것"을 단정하지 말고 **바이트 비교로 실측**(특히 아카이브 보존).
- **A/B 자가검증**: 변환 가드는 "변환 스킵 뮤턴트면 반드시 FAIL"을 증명(허위 오라클 금지 — `false-oracle-ab`).

착수 전 자문 7문:
1. 로컬 세이브냐 서버 DB냐? (성격이 다름 — §0)
2. 변환이 결정론적인가?(랜덤·시계 없나)
3. 바꿀 필드만 만지고 나머지는 보존하나?
4. **과거 아카이브/히스토리를 소급 훼손하지 않나?**(격리 확인 + 바이트 비교)
5. 리플레이/재계산에 소급되나? 소급돼도 안전한가?
6. 일회성 게이트인가?(version < N / Expand/Contract 단계)
7. 실패 시 복구/롤백 경로가 있나?(세이브 복구 채널 / DB 백업)

## 4. 실사례 — 특성 v4→v5 (2026-07-27)

- **무엇**: 특성 20종 확장(상시6·반응7·맥락2·상태5) 전에 만든 세이브의 선수가 옛 규칙 특성(무특성 0개·반응형 없음)을 유지해 신규 기능이 안 보임(실기기서 곽다서=특성 0개 확인).
- **어떻게**: `SAVE_VERSION` 4→5, `migrateSave` v4→v5 단계에서 base 선수 전원 `traits`를 `rollTraits(id)`로 재부여(§1.2 결정론·§1.3 필드만·§1.4 아카이브 무접촉).
- **검증**: 전 선수 1~3개·상극 0·반응형 등장 + 결정론 2회 동일 + **아카이브 바이트 불변** + traits외 불변 + version 게이트 일회성 + A/B(스킵 뮤턴트 FAIL). 회귀 세이브 가드 8종·골든 PASS. 가드 `tools/_dv_trait_migrate.ts`.
- **교훈**: `p.traits ? p : ...`의 `[]`(빈 배열) truthy 함정 — "값이 있으면 유지"가 **0개도 유지**해 옛 규칙을 고착. 마이그레이션이 그 고착을 푸는 정공법(commitPlayerBase 분기 자체는 무접촉, 재부여 후엔 전원 비어있지 않아 실질 무해).
